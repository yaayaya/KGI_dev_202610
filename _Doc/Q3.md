# Q3：借券利息結算與監控

依使用者指定，結算操作與維運監控全部使用 Vue，入口為 `/interest`，與 Q1、Q2 共用外框及選單。

## 計息規則與範圍

原題未提供本金、利率及計息基礎，因此本版採明確的示範規則，合成資料不代表真實合約或券商帳務：

```text
單日利息 = 本金 × 年利率 ÷ 365
```

- 本金為 `DECIMAL(18,4)` 的正值；年利率為 `DECIMAL(9,8)` 的正值，例如 3% 保存為 `0.03000000`。
- C# 使用 `decimal`，每筆以 `MidpointRounding.AwayFromZero` 四捨五入至四位小數，再寫入及加總；不採總額先算後取位。
- `Interest_Source` 保存每批的固定本金及利率，與 Q2 擔保品分開。應用程式不提供修改來源、批次 CRUD 或手動覆寫預計總額。
- `Expected_Amt` 獨立保存，禁止結算時用本次明細總額取代，以保留校驗意義。
- 原題同時描述「完全一致」及「差異大於 0.0001 才回滾」；本版依明確門檻，絕對差異 **大於 0.0001** 失敗，等於 `0.0001` 可成功。若業務要求零差異，須調整規則與邊界測試。
- SQL 加總及差異運算保留四位小數，避免 `SUM` 型別提升造成相減時縮位。

本版完成手動啟動、背景結算與監控；凌晨排程、失敗批次重試及正式計息來源串接不在本版範圍。

## 操作方式

1. 依 [README](../README.md#啟用-q3-借券利息結算) 套用腳本並啟用 Q3。
2. 開啟「借券利息結算」，選取批次查看狀態與已提交明細。
3. 對待處理批次按「啟動結算」。送出時按鈕顯示 Loading 並停用；受理後由背景工作者執行。
4. Vue 每五秒讀取批次及選中批次的快照，顯示進度條、百分比與最後更新時間；背景更新保留選取及捲動位置。
5. 成功後顯示 100% 與已提交明細；失敗時顯示紅色告警區及持久保存的錯誤日誌。

輪詢失敗保留舊資料並提示資料可能過期，不視為結算失敗。啟動請求結果不明時先查狀態，不自動重送；離開頁面只取消監控讀取，不會取消已受理結算。

## 狀態與交易

| 狀態 | 意義 | 可否啟動 |
| --- | --- | --- |
| 0 | 待處理 | 可以 |
| 1 | 已受理／處理中 | 不可以 |
| 2 | 結算成功 | 不可以 |
| 9 | 失敗或程序中斷 | 不可以，需人工處理 |

- 啟動使用 SQL 原子條件更新 `0 → 1`，同批並行請求只有一次受理。
- 資料庫中的狀態 1 為持久工作佇列，避免只使用記憶體佇列而在重啟後漏掉工作。
- 工作者使用批次專屬的 SQL session 鎖，取得後重新讀取狀態；同批只有一個工作者執行。
- 開始時間為 null 表示尚未開始；取得鎖後先保存開始時間。若後續工作者拿到鎖仍發現狀態 1 且已有開始時間，會標記中斷失敗，避免自動重跑。
- 明細寫入、SQL 總額校驗及成功狀態在同一交易內；失敗會回滾全部明細，再以獨立操作保存狀態 9 及錯誤訊息。
- 進度另以連線／短交易發布，明細交易完成前不提前鎖住批次主列。100% 僅表示成功提交，失敗保留最後已發布進度。
- 處理中的監控查詢不讀取未提交明細；API 只在成功後提供明細總額，避免輪詢被長交易阻塞。
- 工作者使用服務停止的取消訊號，不使用 HTTP 請求取消訊號；關閉頁面不影響結算。

## API

| 方法與路徑 | 用途 | 成功狀態 |
| --- | --- | --- |
| `GET /api/interest/batches` | 批次列表與進度 | 200 |
| `GET /api/interest/batches/{id}` | 單批快照與已提交明細 | 200 |
| `POST /api/interest/batches/{id}/settlement` | 受理結算，不需 request body | 202 |

列表回傳 `batchId`、`expectedAmt`、`processStatus`、`progressRate`、`startedTime`、`finishedTime`、`errorMessage`。單批回應為 `batch`、`calculatedAmt`、`details`；未成功時總額為 null、明細為空。金額固定四位小數字串，狀態／進度為整數，時間為 UTC ISO 8601 字串或 null。

啟動成功附上 `Location` 查詢網址；批次不處於待處理狀態回傳 `409`，無效編號回傳 `400`，查無批次回傳 `404`，未啟用功能回傳 `503`。錯誤沿用 ProblemDetails，系統詳細例外僅留在伺服器日誌。

## 資料庫與維護入口

| 資料表 | 用途 |
| --- | --- |
| `Interest_Batch` | 預計總額、狀態、已發布進度、UTC 起訖時間與錯誤訊息 |
| `Interest_Source` | 批次＋合約唯一的固定本金與利率快照 |
| `Interest_Detail` | 成功結算結果；批次＋合約唯一並關聯來源 |

新環境使用既有全量建表、索引與預載流程；既有資料庫使用 [AddQ3Interest.sql](../Kgi.Tests/Database/Scripts/InitTestDb/DbScript/AddQ3Interest.sql) 後再執行 [Preload.sql](../Kgi.Tests/Database/Scripts/InitTestDb/Preload.sql)。增量腳本可重跑且保留既有資料；預載只補缺少的批次與待處理批次來源，不重設結算結果。

| 合成批次 | 來源數 | 實算總額 | 預計總額 | 預期結果 |
| --- | ---: | ---: | ---: | --- |
| `20261029_INT` | 1,000 | 22230.2344 | 22230.2344 | 成功 |
| `20261028_INT` | 10 | 441.3004 | 441.3006 | 差異 0.0002，回滾失敗 |
| `20261027_INT` | 5 | 720.4026 | 720.4026 | 成功 |

所有來源直接列於 SQL `VALUES`，共 1,015 筆，初始化不建立結算明細。預載不覆寫既有資料，因此上述預期值以本版新初始化的來源為準。

後端入口為 `Kgi.Api/Features/Interest/`，維持 Controller → Service → Dao → SQL；前端入口為 `Kgi.Web/src/features/interest/`，由 composable 管理輪詢及送出狀態。契約使用既有 OpenAPI／Orval 流程，不手改生成檔。

## 驗證方式

後端使用一般方式執行 `dotnet test Kgi.Tests/Kgi.Tests.csproj`。本版本只使用 `KGI`，DB/API 測試共用 API 的 `ConnectionStrings:Kgi`，設定 `KGI_RUN_DB_TESTS=1` 才執行，不會重建資料庫；跳過不代表通過。測試批次每次使用唯一編號，最後只刪除自行建立的批次、來源及明細。

Q3 測試主機移除自動輪詢工作者，改以同一個結算 Service 處理明確指定的測試批次；不會掃描及執行既有使用者工作。增量驗證只比較既有資料，不修改原有示範批次或來源。

必要驗證包含：逐筆捨入、來源精度驗證、並行啟動僅一次受理、成功不能重跑、`0.0001／0.0002` 門檻、失敗無部分明細且日誌仍在、明細被鎖時進度仍可讀、第二工作者不誤判存活工作，以及重啟後的佇列與中斷處置。

前端人工檢查：

1. 桌面與手機選單可切換 Q1、Q2、Q3，原有功能維持正常。
2. 連點或雙視窗啟動只有一次受理；送出、處理中及終態的按鈕狀態正確。
3. 處理中重開頁面可接續監控，切換批次不被舊回應覆蓋。
4. 成功顯示總額及明細；故意不符批次顯示紅色告警與日誌。
5. 斷線保留舊快照，恢復後更新；輪詢不重設選取或捲動，離頁停止監控請求。
